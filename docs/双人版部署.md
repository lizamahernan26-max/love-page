# 心网 0.4 双人版：运行与部署

状态：真实后端已实现，尚未选择主机或发布公网。以下是可执行的本机步骤与待适配的部署方案，不代表已经上线。

## 本机使用

需要 Node.js 24.14 或更新版本；当前电脑已用 24.19.0 验证。不需要 npm install。

1. 双击项目根目录 `start.cmd`，或运行 `npm start`，打开 `http://127.0.0.1:8790/`。
2. 点击“账号与绑定”，在本机创建第一个账号。账号用 3—24 位小写字母、数字或下划线，密码至少 12 字符。
3. 登录后生成邀请码。让对方使用自己的浏览器创建第二个账号，填写该码。两个账号建立后停止新账号注册。
4. 两人分别登录自己的账号。“仅本人可见”由服务器限制；“两人共享”在当前绑定关系内同步，只有作者能编辑和删除。
5. 共同姓名与纪念日也会同步；音乐音量仍按设备单独保存。

`data/xinwang.sqlite` 是持久数据库。停止服务或重启电脑不会主动清除记录。不要删除 `data`，也不要把真实数据库放进 `dist`、版本库或网页公开目录。

## 手机开发预览

先在电脑本机创建首个账号，再双击 `start-phone.cmd`，或运行 `npm run start:phone`。脚本显示当前私有局域网 IP 和 8791 端口；两台测试手机连接同一 Wi-Fi 即可访问。它和本机双人版共用数据库。切换网络后按脚本新输出的地址使用。

**局域网入口是 HTTP 开发验证，传输未加密。仅用测试密码和测试文字。** 正式手机使用需要下方 HTTPS 部署。它不是异地使用网址，不修改防火墙，也不自动配置路由器。首次账号只能在电脑本机初始化，不能从局域网抢先创建。

原来 `npm run preview` / `node scripts/serve.mjs` 的 8787 入口仍是本地原型；它没有真实账号。原型记录与账号记录分开，不会自动上传。请认准有“账号与绑定”的 8790/8791 双人版入口。

## 已实现的权限与同步规则

| 内容或操作 | 本人 | 当前绑定的对方 | 未绑定账号 |
| --- | --- | --- | --- |
| 仅本人可见的记录 | 可读写删 | 不返回内容、ID 或条数 | 不返回 |
| 当前关系中的共享记录 | 作者可读写删 | 可读，不能改删 | 不返回 |
| 解除绑定前的共享记录 | 只保留作者自己的记录 | 不再能读取作者记录 | 不返回 |
| 共同姓名、纪念日 | 双方可修改 | 双方可修改 | 不可操作 |

网页前台可见时约每 5 秒同步一次；重新聚焦、恢复联网或点“立即同步”也会读取。后台不保持持续轮询。同步不是已读回执，页面没有虚构对方在线或已读状态。

每条记录和共同设定都带版本号；另一设备先改过时拒绝覆盖，草稿仍在。新建请求带幂等编号，网络重试不会重复写入。没有离线队列，断网时不能假装保存成功。

邀请码随机生成、24 小时有效、一次使用；数据库只存摘要。再次生成会使旧码失效。解除绑定需要自己的密码；重新绑定不会自动把旧共享记录发给新关系。对方已看过或自行复制的内容无法收回。

## 正式部署前需要确定

- 一台能长期运行 Node.js 24.14+ 的主机，使用持久本地磁盘；初版按单实例运行，不用会随重启清空文件的无状态函数平台。
- 一个 HTTPS 域名和反向代理；Node 服务只监听本机回环地址。选定主机后再适配系统服务、证书和自动备份。
- 每个账号自己设置密码。当前无短信/邮件密码找回，不能把展示姓名当作身份。

构建部署包：

```powershell
npm run package:server
```

输出 `deploy-output/` 包含前后端、字体、百合、音乐、配置示例与本文，**不包含实际账号数据库、.env、测试、原件和备份**。若目录中已有额外文件，打包停止且不删除它们。只有 `dist/` 静态文件不能实现双人功能。

部署机器上的 `.env` 示例（真实密钥只写在受控配置或密钥管理中）：

```dotenv
NODE_ENV=production
PORT=8790
XINWANG_HOST=127.0.0.1
PUBLIC_ORIGIN=https://your-domain.example
XINWANG_TRUST_PROXY=loopback
XINWANG_DB_PATH=/srv/xinwang-private/xinwang.sqlite
# 空数据库首个账号使用的初始化密钥，至少 32 字符；实际值不要提交到代码：
# XINWANG_SETUP_KEY=
```

`PUBLIC_ORIGIN` 必须是精确 HTTPS 来源，不带末尾斜杠。程序在 production 下缺少 HTTPS 来源会拒绝启动；正式模式也拒绝没有受信任 HTTPS 代理标记的请求。新部署的空数据库若从公网初始化，需要由维护者设置初始化密钥；创建首个账号后该初始化入口关闭。

Caddy 配置草案（先将域名指向主机，实际安装与系统服务按选定主机处理）：

```caddyfile
your-domain.example {
    reverse_proxy 127.0.0.1:8790 {
        header_up Host {host}
        header_up X-Forwarded-Proto {scheme}
    }
}
```

代理必须在同机回环地址转发，并覆盖协议头。程序校验 Host、精确 Origin、CSRF 令牌与会话，不接受客户端自行声明作者身份。[Caddy 反向代理文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

## 数据库备份与恢复

运行 `npm run backup:db`，使用 Node SQLite 在线备份接口生成一致的数据库副本，默认放在 `data-backups/`；指定已有文件时会拒绝覆盖。备份可在服务仍运行时生成，不是简单复制正在使用的 WAL 数据库主文件。[Node SQLite backup](https://nodejs.org/api/sqlite.html#sqlitebackupsource-db-path-options)

数据库备份包含两个人全部记录、密码摘要和会话。应由站点维护者保管，与用户界面的“导出我的记录”分开。备份文件没有端到端加密，不能公开上传。若备份失败产生不完整的新文件，脚本不会把它当成功备份；保留错误现场后检查磁盘与权限。

恢复时先停止全部心网服务，另外保留当前数据库及相关 WAL/SHM 文件；将确认可读的备份用于一个新的数据库路径，通过 `XINWANG_DB_PATH` 指向它再启动。不要在服务运行时覆盖原文件。恢复旧快照可能带回当时的会话，启用前可在停服维护时清空 sessions 表，使双方重新登录；这项操作只清会话，不删除心里话。

## 隐私与加密边界

本版提供**两个账号之间的服务端权限隔离**。密码使用独立盐的 scrypt 摘要；会话存摘要，浏览器使用 HttpOnly、SameSite=Strict Cookie，HTTPS 部署时加 Secure / __Host- 前缀；写操作还检查来源与 CSRF。[OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)、[会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

记录正文目前保存在服务器数据库中，**服务器维护者和有数据库访问权限的人仍可能查看**；没有实现数据库正文加密或端到端加密。因此“仅本人可见”指普通账号之间的访问权限，不能解释为托管商、管理员或已控制设备的人都无法读取。HTTPS 只解决传输链路的一部分保护，不能替代端到端加密。

旧版浏览器 localStorage 中的记录不归属于账号，仍按旧版未加密本地副本处理。双人版不自动读取、上传或删除它们。可在原型入口导出，再在自己的账号里预览并导入；旧文件中的共享分类也先转成私密。迁移成功后，是否删除旧副本由用户自行决定。

原音乐和原始姓名、纪念日继续沿用。正式发布前需确认展示及音乐使用范围。本轮没有注册云账号、购买服务或公开发布网站。
